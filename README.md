# AI 패션 ERP

> 의류 사업을 처음 시작한 판매자를 위해 **발주 → 입고 검수 → 판매 → 반품**을 한 줄기로 관리하고, 불량률과 반품 원인을 다음 발주량과 상품별 수익성에 반영해주는 ERP.

**해커톤 10조** · React + FastAPI + SQLite + LLM API

---

## 왜 만드는가

의류 사업을 처음 시작한 판매자는 발주, 입고 검수, 판매 관리, 반품 처리, 재고 파악, 정산을 대부분 직접 처리합니다. 데이터가 거래처 카톡, 엑셀, 쇼핑몰 관리자 페이지에 흩어져 있으면 이런 문제가 생깁니다.

- **얼마나, 언제 발주해야 할지 모른다** — 판매량만 보고 발주하다 품절이나 과잉 재고가 생긴다
- **불량을 받고도 그냥 넘어간다** — 거래처별·상품별 기록이 안 남아 다음 발주에 반영되지 않는다
- **반품 사유를 건별로 읽는다** — 반복되는 문제를 발견하기 어렵다
- **실제로 남는 돈을 모른다** — 수수료·광고비·배송비·반품 처리비·불량 손실을 따로 계산해야 한다
- **네 가지가 서로 연결되지 않는다**

## 핵심 가치

**발주부터 반품까지 한 줄기 데이터로 관리하고, 불량률과 반품 원인을 다음 발주량과 수익성에 자동으로 반영한다.**

지표를 보여주는 데서 끝나지 않고 다음에 무엇을 확인하고 결정해야 하는지 제안합니다. AI는 반품 사유를 분류하고 원인 후보를 제시하지만, 발주량·거래처 변경·상품 수정은 **사용자가 최종 결정**합니다.

## 필수 기능 4개

| 영역 | 기존의 수작업 | 시스템이 지원하는 기능 | 주요 결과물 |
|---|---|---|---|
| **불량률** | 입고 불량을 그때만 보고 넘어감 | 발주 건·거래처·상품별 입고 불량률과 불량 유형 집계 | 거래처별 불량률 비교, 불량 유형 비중, 불량 손실 금액 |
| **재고 및 발주** | 판매량과 감으로 재주문 | 양품 기준 재고, 판매 추세·리드타임·불량률을 반영한 권장 발주량 | 재고 소진 예상일, 발주 필요 시점, 권장 발주량과 산출 근거 |
| **정산 수익** | 수수료·광고비·배송비·반품비를 따로 계산 | 상품별 순매출·비용·불량 손실·추정 기여이익 계산 | 상품별 수익성 표, 비용 구성, 적자 상품 표시 |
| **반품 원인 분석** | 반품 사유를 하나씩 읽고 분류 | AI가 자유 서술형 사유와 후기를 범주화하고 반복 패턴 요약 | 주요 반품 원인, 원문 근거, 개선 체크리스트 |

> **AI를 쓰는 곳은 반품 원인 분석 한 곳입니다.** 나머지 세 영역은 공식이 명시된 계산과 집계로 처리하고, 산출에 사용한 데이터와 가정을 함께 표시합니다.

## 4개 기능이 서로를 보정한다

네 영역을 따로 보여주는 것이 아니라, 하나의 데이터에서 서로를 보정하게 만드는 것이 이 프로젝트의 핵심입니다.

```text
[발주·입고 검수] ──불량률──┬──→ 양품 입고 수량 ──→ [재고]
                           ├──→ 불량 손실 금액 ──→ [정산 수익]
                           └──→ 불량률 보정 ────→ [권장 발주량]
                                                       ↑
[판매] ──일평균 판매량────────────────────────────────┘
   │
   └──→ 총매출 ──→ [정산 수익]

[반품] ──반품률───→ 재판매 가능분 ──→ [재고]
   │   └─반품 금액·처리비 ──────→ [정산 수익]
   │
   └──AI 사유 분류──→ `품질·마감` 범주 ⇄ 입고 불량 유형 대조 ──→ [거래처 점검]
                    └─→ `사이즈·핏` 범주 ──→ 상품 개선 체크리스트
```

| 연결 | 의미 |
|---|---|
| 불량률 → 발주량 | 필요 수량 100장, 불량률 5%면 **106장**을 발주해야 양품 100장을 받는다 |
| 불량률 → 수익성 | 불량 수량 × 원가를 비용으로 반영해 실제 남는 돈을 계산한다 |
| 반품 `품질·마감` ⇄ 입고 불량 유형 | 고객이 말하는 품질 문제와 입고 검수에서 잡힌 불량이 같은 방향인지 확인한다 |
| 반품 재판매 가능분 → 재고 | 반품을 전부 손실로 보지 않고 재판매 가능한 수량만 재고로 되돌린다 |
| 반품률 + 불량률 → 거래처 평가 | 두 지표를 함께 봐야 상품 설계 문제와 생산 품질 문제를 구분할 수 있다 |

이 연결이 "대시보드 4개"와 "운영을 편하게 해주는 ERP"의 차이입니다.

## 지표 공식

AI를 쓰지 않는 세 영역은 공식을 문서에 못 박고, **산출에 사용한 모든 숫자를 화면에 표시**합니다.

### 불량률

```
입고 불량률 (%)  = 불량 수량 ÷ 검수 수량 × 100
양품 입고 수량    = 입고 수량 − 불량 수량
불량 손실 금액    = 불량 수량 × 상품 원가
거래처 불량률     = 누적 불량 수량 ÷ 누적 검수 수량 × 100
```

분모는 **검수 수량**으로 통일합니다. 전수 검수가 아닌 경우 표본 수를 함께 표시합니다.
급증 판정은 통계 검정 없이 **발주 건 불량률 ≥ 해당 상품 평균 × 1.5** 규칙을 씁니다.

### 재고 및 발주

```
현재 재고        = 누적 양품 입고 − 누적 판매 수량 + 재판매 가능 반품 수량
일평균 판매량     = 최근 N일 판매 수량 ÷ N          (기본 N = 7)
재고 소진 예상일  = 현재 재고 ÷ 일평균 판매량
발주 필요 시점    = 재고 소진 예상일 − 리드타임

필요 수량        = 일평균 판매량 × (리드타임 + 목표 커버일) − 현재 재고
권장 발주량       = 필요 수량 ÷ (1 − 입고 불량률)    ← 불량률 반영
최종 발주량       = 권장 발주량을 최소 발주 수량 단위로 올림
```

수요예측 모델을 만들지 않습니다. 판매 기간이 짧으면 **"추정 신뢰도 낮음"** 을 표시합니다.

### 정산 수익

```
순매출          = 총매출 − 반품 금액
불량 손실        = 불량 수량 × 원가                 ← 불량률 영역에서 전달
추정 기여이익     = 순매출 − 상품 원가 − 플랫폼 수수료 − 변동비 − 불량 손실
기여이익률 (%)    = 추정 기여이익 ÷ 순매출 × 100
```

비용 데이터가 누락되면 정확한 순이익으로 표시하지 않고 **"입력된 비용 기준 추정 기여이익"** 으로 표기합니다. 세무·회계 신고를 대체하는 서비스가 아닙니다.

### 반품 원인 분석 (AI)

```
반품률 (%) = 반품 수량 ÷ 판매 수량 × 100
```

**분류 체계** — `사이즈·핏 문제` · `색상·이미지 차이` · `원단·촉감·두께` · `품질·마감` · `배송·포장` · `단순 변심` · `기타·판단 불확실`

**AI 출력은 네 블록을 반드시 분리합니다.**

| 구분 | 내용 | 예시 |
|---|---|---|
| 관측된 사실 | 데이터에서 직접 확인되는 수치 | 반품 23건 중 10건(42%)이 사이즈·핏, "허벅지" 언급 7건 |
| 가능한 원인 | 단정하지 않는 원인 후보 | 허벅지 둘레 또는 사이즈 안내가 고객 기대와 다를 가능성 |
| 추가 확인 사항 | 사용자가 직접 확인할 것 | 사이즈별 실측 치수, 패턴, 상품 페이지 사이즈 안내 |
| 개선 체크리스트 | 등록 가능한 작업 | 다음 샘플 전 허벅지 실측표 검토 / 페이지에 실측 치수 추가 |

모든 주요 의견에 **원문 예시**를 붙입니다. 근거가 부족하면 원인을 확정하지 않고 **"판단하기 어려움"** 으로 반환합니다. 반품 사유는 고객이 작성한 이유이며 검증된 실제 원인이 아닙니다.

## 시연 시나리오

**와이드 데님 팬츠 — 재발주 판단**

1. **불량률** — 이번 발주 건 입고 불량률 8%, 같은 거래처 평균(3%)보다 높음. 불량 유형은 봉제 불량에 집중
2. **재고** — 양품 기준 40장, 최근 7일 평균 6장/일 → 약 6.7일 후 소진. 리드타임 10일이므로 **이미 발주 시점을 지남**
3. **발주** — 필요 수량 104장(6.0 × 24 − 재고 40), 불량률 8% 반영 113장 → MOQ 50장 단위로 올려 **150장** 권장 (산출에 쓴 숫자 전부 표시)
4. **반품 분석** — AI가 분류: 전체 반품 중 42%가 `사이즈·핏`, "허벅지가 좁다" 표현 7건 반복, 원문 예시 제시
5. **연결** — 반품 `품질·마감` 9%가 입고 검수의 봉제 불량과 같은 방향을 가리킨다고 표시 (단정하지 않고 확인 항목으로)
6. **수익** — 추정 기여이익률 11%. 불량 손실과 반품 처리비가 비용의 31% 차지
7. **조치 등록** — "거래처에 봉제 불량 전달 + 다음 입고 전수 검수"(담당·마감일), "허벅지 둘레 실측표 재확인"

> 불량률이 높다는 이유만으로 거래처 변경을 권고하지 않습니다. 표본 수, 검사 기준, 납기, 단가를 함께 확인하도록 안내합니다.

## 아키텍처

```text
[사용자]
   ↓
[React 프론트엔드]
   ├─ 홈 대시보드 (4개 영역 요약)
   ├─ 재고·발주
   ├─ 불량률
   ├─ 수익성
   └─ 반품 분석 + 개선 조치
          ↓ HTTP / JSON
[FastAPI 백엔드]
   ├─ CSV 검증 및 적재
   ├─ 지표 계산 (불량률·재고·발주량·기여이익·반품률)
   ├─ AI 분석 호출
   └─ 개선 조치 저장·조회
          ↓
[SQLite]          ← 해커톤에서는 파일 DB

[백엔드 서버 측에서만]
          ↓
[LLM API]
   └─ 반품 사유 분류 및 개선 체크리스트 생성
```

> 🔒 AI API 키를 프론트엔드 코드에 넣지 않습니다. 반드시 백엔드에서 호출합니다.

### 데이터 모델

| 테이블 | 설명 | 쓰이는 영역 |
|---|---|---|
| `products` | 상품 정보, 판매가, 원가, 리드타임, 최소 발주 수량 | 전체 |
| `suppliers` | 거래처 정보 | 불량률 |
| `purchase_orders` | 발주일·입고일·거래처·발주/입고/검수/불량 수량 | 불량률, 재고·발주 |
| `defects` | 불량 유형별 수량 (발주 건에 연결) | 불량률 |
| `sales` | 판매일·수량·채널·금액 | 재고·발주, 정산 |
| `returns` | 반품 수량·사유·후기·재판매 가능 여부 | 반품 분석, 재고, 정산 |
| `costs` | 채널 수수료율, 광고비, 배송비, 반품 처리비 | 정산 |
| `tasks` | 개선 조치, 담당자, 마감일, 상태 | 반품 분석, 불량률 |

**재고는 별도 테이블을 만들지 않고 계산으로 구합니다** (양품 입고 − 판매 + 재판매 가능 반품).

### API

| Method | Endpoint | 설명 |
|---|---|---|
| `POST` | `/api/imports` | CSV 업로드 및 검증 |
| `GET` | `/api/dashboard` | 홈 요약 (4개 영역 핵심 지표) |
| `GET` | `/api/quality/defect-rates` | 불량률 — 상품·거래처·발주 건별 |
| `GET` | `/api/inventory` | 재고 현황 및 소진 예상일 |
| `GET` | `/api/inventory/reorder` | 권장 발주량 + 산출 근거 |
| `GET` | `/api/profit` | 상품별 수익성 |
| `GET` | `/api/returns/rates` | 반품률 |
| `POST` | `/api/returns/analyze` | AI 반품 원인 분석 요청 |
| `POST` | `/api/tasks` | 개선 조치 등록 |
| `PATCH` | `/api/tasks/{taskId}` | 조치 상태 변경 |

> 경로는 설계 예시이며, 팀이 응답 형식을 합의한 뒤 확정합니다. **개발 시작 1시간 안에 예시 JSON을 커밋해 공유합니다.**

### 반드시 구현

- [ ] 데모 데이터 적재 + 고정 스키마 CSV 업로드·검증
- [ ] **불량률** — 발주 건·상품·거래처별 불량률, 불량 유형 비중, 평균 1.5배 급증 배지

- [ ] **정산 수익** — 상품별 순매출·비용 구성·추정 기여이익·기여이익률, 적자 상품 강조
- [ ] **반품 원인 분석** — 반품률, AI 사유 분류, 반복 패턴 요약, 원문 근거, 개선 체크리스트

- [ ] 홈 대시보드 4개 영역 요약 카드

### 여유가 되면

- [ ] 사이즈·색상별 반품·불량 상세 분석
- [ ] 반품 `품질·마감` 범주와 입고 불량 유형 자동 대조
- [ ] 거래처별 품질·단가·납기 비교 화면
- [ ] 목표 커버일 변경 시나리오 비교
- [ ] 조치 전후 불량률·반품률·기여이익 비교
- [ ] 채널별 수익성 분리

### 데모 데이터

실제 고객 개인정보 없이 가상 데이터로 구성합니다.

- 상품 6~8종, 거래처 2~3곳
- 발주·입고 12~15건 — 그중 **1건은 불량률이 평균의 2배 이상**
- 판매 데이터 최근 30일
- 반품 40~60건 — 자유 서술형 후기 포함, 한 상품에 `사이즈·핏` 의견이 **반복적으로** 나타나게
- 적어도 **1개 상품은 기여이익이 음수**

## 팀

| 팀원 | 주 담당 | 핵심 책임 |
|---|---|---|
| **윤지** | 프론트엔드·UI | 홈 대시보드 + 재고·발주 + 불량률 + 수익성 화면, 공통 컴포넌트 |
| **태연** | 백엔드 | SQLite 스키마, CSV 적재, 4개 영역 지표 계산 API, AI 호출 연동 |
| **서영** | AI | 반품 분석 프롬프트, 입출력 JSON 스키마, 개선 체크리스트 생성 |
| **예나** | AI 검증 → FE 보조 | 분류 테스트·출력 검증·실패 시 폴백 응답, 이후 반품 분석 화면 |
| **시환** | 데이터 | 데이터 사전, 샘플 데이터, 4개 영역 계산 공식 정의와 검증값 |

### 협업 규칙

1. **지표 공식과 분모를 가장 먼저 합의한다.** 불량률의 분모, 재고 계산식, 기여이익 항목이 담당자마다 달라지지 않게.
2. **AI 출력 JSON과 API 예시를 개발 시작 1시간 안에 커밋한다.** 프론트엔드는 이 mock JSON으로 개발을 시작한다.
3. **지표 응답에는 산출에 사용한 숫자를 함께 담는다.** 화면에서 근거를 보여줘야 하므로 결과값만 반환하지 않는다.
4. **관측값과 AI 추정을 구분한다.** 계산된 수치와 AI가 제시한 원인 후보를 섞어 표시하지 않는다.
5. **샘플 데이터로 전체 흐름을 먼저 검증한다.** 업로드 → 지표 계산 → AI 분석 → 조치 등록까지 재현 가능하게.
6. **데이터 부족 표시를 통일한다.** "추정 신뢰도 낮음", "표본 수 부족", "일부 비용 미입력".
7. **최종 통합 테스트는 전원이 참여한다.** 시연 시나리오를 2회 이상 리허설한다.

## 검증 기준

"AI가 정확하다"라고만 주장하지 않고 아래를 확인합니다.

- [ ] 업로드 데이터의 필수 항목 오류를 감지하는가?
- [ ] **불량률** 계산이 수작업과 일치하는가? 분모(검수 수량)와 표본 수를 표시하는가?
- [ ] **재고** 계산이 양품 입고 − 판매 + 재판매 가능 반품과 일치하는가?
- [ ] **권장 발주량**에 불량률이 실제로 반영되고, 산출에 쓴 숫자가 모두 보이는가?
- [ ] **기여이익**에 불량 손실과 반품 처리비가 포함되는가? 누락 비용을 명시하는가?
- [ ] **반품 AI 분류**가 유사 표현을 일관되게 같은 범주로 묶는가?
- [ ] AI가 제시한 주요 의견에 **원문 근거**가 연결되어 있는가?
- [ ] 데이터가 부족할 때 과도한 확신을 피하는가?
- [ ] 개선안이 담당자·마감일이 있는 구체적 작업으로 이어지는가?
- [ ] **AI 호출이 실패해도 시연이 끝까지 진행되는가?**

## 범위에서 제외한 것

| 제외 항목 | 이유 |
|---|---|
| 생산 라인·로트 단위 불량 분석 | 처음 사업하는 판매자는 생산 라인 데이터가 없다. 입고 검수 단위로 축소 |
| AI 품질 원인 후보 생성 | AI 파이프라인 2개 = 프롬프트·스키마·테스트 2세트. AI는 반품 분석 한 곳만 |
| 공장 변경 검토 플로우 | 비교 가능성 검증·개선 계획 요청·관찰 기간은 단독으로 하루치 |
| 상품 기획 피드백 | 반품 분석의 개선 체크리스트와 상당 부분 중복 |
| 영업이익 영향 분석 | 추정 영업이익은 가정이 너무 많다. 기여이익까지만 |
| 열 이름 매핑 UI, XLSX 지원 | 인코딩·타입 변환·매핑 UI는 시간 대비 효과가 낮다 |
| PostgreSQL / Supabase | 프로비저닝·마이그레이션·접속 오류 위험. SQLite 파일 DB |
| 통계적 유의성 검정 | 표본이 작아 의미가 없다. 평균 × 1.5 규칙 + 표본 수 표시 |

**기능을 줄인 것이 아니라, 처음 사업하는 판매자가 하루에 실제로 쓰는 네 가지 판단** — 얼마나 발주할지 / 불량이 어디서 오는지 / 왜 반품되는지 / 실제로 남는지 — **에 집중했습니다.** 생산 라인 단위 품질 분석과 거래처 전환 검토는 데이터가 쌓인 다음 단계입니다.
