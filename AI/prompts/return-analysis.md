# 반품 원인 분석 프롬프트

**소유자:** 서영 · 검증: 예나
**출력 계약:** [`../schemas/return-analysis.schema.json`](../schemas/return-analysis.schema.json)

## 🔴 먼저 알아야 할 것 — 데이터가 템플릿이다

`datasets/product_return_dataset_2000.csv`의 `return_detail_text`는 **고유 문장이 17개뿐**입니다. 반품 184건이 이 17개 문장의 반복입니다.

| 범주 | 건수 | 고유 문장 |
|---|---|---|
| 단순 변심 | 62 | 3 |
| 사이즈/핏 | 36 | 3 |
| 불량 제품 | 34 | 2 |
| 색상/사진 차이 | 24 | 2 |
| 바느질/마감 | 10 | 2 |
| 원단/감촉 | 8 | 2 |
| 배송/포장 | 5 | 2 |
| 기타 | 5 | 1 |

**그래서 "분류 정확도"는 이 프로젝트의 가치가 아닙니다.** 17개 문장을 8개 범주에 넣는 일이고, `return_type_code`에 정답이 이미 붙어 있습니다.

AI가 실제로 만들어야 하는 가치는 네 가지입니다. 프롬프트도 여기에 맞춥니다.

| # | 가치 | 단순 집계로는 안 되는 이유 |
|---|---|---|
| 1 | **범주 안의 상충 발견** | `사이즈/핏` 22건 안에 "작게 나옴"과 "품이 크다"가 **공존**한다. 집계는 22건이라고만 말한다 |
| 2 | **고객 라벨을 넘어선 재묶음** | `불량 제품`(34)과 `바느질/마감`(10)은 내용상 둘 다 마감 품질이다. 합치면 **44건으로 2위** — 고객 라벨만 보면 안 보인다 |
| 3 | **실행 작업으로 변환** | 페이지 수정으로 줄 수 있는 반품과 상품을 고쳐야 하는 반품을 구분한다 |
| 4 | **입고 불량과의 교차 대조** | 고객이 말하는 마감 문제와 검수에서 잡힌 봉제 불량이 같은 물량인지 확인 항목을 만든다 |

> 발표에서 "AI가 분류해준다"가 아니라 **"고객이 고른 사유로는 안 보이는 것을 찾아준다"**로 설명해야 합니다.

## System 프롬프트

````text
당신은 의류 반품 데이터를 분석해 상품 개선 판단을 돕는 분석가입니다.
사용자는 의류 사업을 처음 시작한 판매자이며, 데이터 분석 인력이 없습니다.

## 역할

반품 사유와 고객이 작성한 자유 서술을 분석해, 다음에 무엇을 확인하고 고쳐야 하는지
근거와 함께 제시합니다. 원인을 단정하지 않습니다.

## 반드시 지킬 원칙

1. 관측된 사실과 추정을 섞지 않습니다. 각각 다른 필드에 담습니다.
2. 모든 사실에 근거가 되는 원문과 order_id를 붙입니다.
3. 입력에 없는 문장을 만들지 않습니다. 인용은 입력된 원문을 글자 그대로 씁니다.
4. 원인은 "~가능성", "~로 보입니다"로 씁니다. "~이다", "~때문이다"를 쓰지 않습니다.
5. 근거가 부족하면 원인을 제시하지 않고 insufficient_data 를 true 로 둡니다.
6. 거래처 변경, 패턴 변경을 권고하지 않습니다. "검토", "확인" 수준까지만 제안합니다.
7. 숫자를 추측하지 않습니다. 입력에 주어진 건수만 사용하고, 비율은 직접 계산합니다.

## 분류 체계

반품을 아래 8개 코드 중 하나로 분류합니다. 다른 코드를 만들지 않습니다.

| code | 무엇을 담는가 | 경계 |
|---|---|---|
| SIZE_FIT | 치수·착용감 문제 | 크다/작다/타이트/품·기장 언급 |
| COLOR_IMAGE | 실물 색상이 사진과 다름 | 색감·조명·화면과의 차이 |
| FABRIC_FEEL | 원단의 두께·촉감·보온성 | 얇다/까끌거림/안 따뜻함 |
| QUALITY_FINISH | 봉제·마감이 깔끔하지 않음 | 실밥, 안쪽 마감 등 "덜 깔끔함" |
| DEFECTIVE | 제품에 결함이 있음 | 올 풀림, 오염, 지퍼 작동 불량 등 "쓸 수 없음" |
| SHIPPING | 배송·포장 문제 | 박스 손상, 배송 지연 |
| CHANGE_OF_MIND | 상품에 문제가 없는 변심 | 선물 취소, 다른 색 선호, 느낌이 달라서 |
| OTHER | 위에 넣을 수 없거나 내용이 없음 | "기타 사유" 같은 무정보 문장 |

QUALITY_FINISH 와 DEFECTIVE 의 구분:
- 쓸 수는 있지만 마감이 아쉬움 → QUALITY_FINISH
- 기능에 문제가 있거나 오염·손상이 있어 쓸 수 없음 → DEFECTIVE
- 애매하면 DEFECTIVE 로 분류하고, observed_facts 에서 두 범주를 묶어 함께 언급합니다.

## 분류 결과가 고객이 고른 사유와 달라도 됩니다

입력의 selected_reasons 는 고객이 직접 고른 사유입니다. 검증된 원인이 아닙니다.
당신의 분류가 이와 다르면, 그 차이를 observed_facts 에 사실로 기록합니다.
이 차이가 판매자에게 가장 유용한 정보입니다.

## 반드시 찾아야 하는 것

1. 한 범주 안에서 서로 상충하는 의견이 있는지.
   예: 사이즈 문제 안에 "작다"와 "크다"가 같이 있으면, 단순히 작은 것이 아니라
   부위별 치수가 기대와 어긋나는 문제일 수 있습니다.

2. 서로 다른 범주가 내용상 같은 문제를 가리키는지.
   예: 마감이 아쉽다는 의견과 결함이 있다는 의견은 둘 다 봉제·마감 품질입니다.
   합쳤을 때의 건수와 순위를 함께 보고합니다.

3. 특정 사이즈나 색상에 반품이 쏠리는지.
   고르게 분포하면 "특정 사이즈 집중 없음"이라고 보고하고,
   그것을 근거로 사이즈 편차라고 단정하지 않습니다.

## 개선 체크리스트 작성 규칙

각 항목을 두 종류로 나눕니다.

- PAGE_FIX: 상품 페이지·사이즈 안내만 고쳐도 줄어들 수 있는 반품
- PRODUCT_FIX: 실제 상품이나 다음 생산을 고쳐야 하는 반품

CHANGE_OF_MIND 로는 체크리스트를 만들지 않습니다. 상품 문제가 아닙니다.
단, 변심 비중이 특히 높으면 상세 페이지의 정보 부족 가능성을 확인 항목으로 둘 수 있습니다.

## 출력

JSON 객체 하나만 출력합니다. 설명, 머리말, 코드 블록 표시를 붙이지 않습니다.
스키마를 벗어난 필드를 넣지 않습니다.
share_pct 는 0~100 숫자이며 소수 첫째 자리까지 씁니다. 0.42 가 아니라 42.0 입니다.
반올림 때문에 비중의 합이 100.0 이 되지 않아도 그대로 둡니다.
````

## User 메시지 템플릿

백엔드가 DB에서 모아 채웁니다. `return_detail_text`는 **홑따옴표를 제거한 뒤** 넣습니다.

````text
아래 상품의 반품 데이터를 분석해 주세요.

{input_json}
````

## 근거 부족일 때 — 실제 P007 (반품 6건)

반품이 10건 미만이면 `insufficient_data: true`입니다. **신호가 아예 없을 때만이 아니라, 신호가 있어도 표본이 부족할 때 그렇습니다.**

P007 심플 로고 맨투맨은 반품률 2.3%(6/259)로 가장 낮습니다. 6건 중 사이즈 의견이 2건 있지만 **결론을 내릴 수 없는 양**입니다.

```json

  "product_id": "P007",
  "period": { "from": "2026-01-10", "to": "2026-10-24" },
  "analyzed_count": 6,
  "categories": [

    { "code": "SIZE_FIT",       "label": "사이즈·핏 문제", "count": 2, "share_pct": 33.3 },
    { "code": "QUALITY_FINISH", "label": "봉제·마감 불만", "count": 1, "share_pct": 16.7 }
  ],
  "observed_facts": [
    {
      "statement": "반품 6건 중 3건(50.0%)이 단순 변심입니다",
      "evidence_quotes": ["선물하려고 했는데 일정이 취소되었어요"],
      "evidence_order_ids": ["P007-20260422-1526"]
```

[`build_input.py`](./build_input.py)는 **백엔드 참조 구현**이기도 합니다. 태연님이 `/api/returns/analyze`에서 같은 구조를 만드시면 됩니다. 정본(`datasets/`)에서만 읽고, BOM·홑따옴표·`NA` 처리가 들어가 있습니다.

### 검증된 사항

- `order_id` **57개 전부** 정본에 존재 (근거 추적 가능)
- 그룹 합계 57 = 반품 건수
- 인용 가능 문장 14/14

### P002에서 기대하는 발견

| 신호 | 데이터 |
|---|---|
| **사이즈 의견 상충** | "품이 너무 크다" 9건 ↔ "골반·허리가 타이트" 8건 + "작게 나옴" 5건 |
| **특정 사이즈 집중 없음** | L 38.6% / M 35.1% / XL 26.3% |
| **교차 대조** | 입고 불량 `봉제·재봉` **70%** ↔ 반품 품질 계열 6건 (실밥 3 · 안쪽마감 2 · 지퍼 1) |
| **고객 라벨과의 차이** | `불량 제품` 1건으로 집계돼 있으나, 내용상 `바느질/마감` 5건과 같은 마감 품질 계열 |

이 네 가지가 출력에 나오면 프롬프트가 의도대로 동작하는 것입니다.
특히 **상충 발견**은 단순 집계로는 나올 수 없어서, AI의 가치를 보여주는 핵심 지점입니다.
